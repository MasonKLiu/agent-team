# RFC-001: AI-Native Engineering Governance & Architecture Standards

* **Status:** Enforced

* **Scope:** All Engineering Teams, Autonomous Coding Agents, CI/CD Pipelines

* **Core Objective:** Maintain a codebase revert rate of $< 0.5\%$ under high-velocity AI-assisted development while eliminating line-by-line human code review bottlenecks.

> **Keyword Definitions (per RFC 2119):**
>
> * **MUST / MUST NOT:** Absolute requirements. Violations will immediately block CI/CD pipelines with zero exceptions.
>
> * **SHOULD / SHOULD NOT:** Default standards. Deviations require quantitative justification attached to the PR verification artifacts.

## 1. Determinism First

### 1.1 No Prompt Patching

* **MUST NOT:** Engineers shall not rely solely on appending instructions to `AGENTS.md`, `.cursorrules`, or system prompts to fix recurring architectural or logic mistakes made by agents.

* **MUST:** Every manual correction made to an agent's output **must** be codified into a deterministic static check (e.g., custom ESLint rule, TypeScript compiler constraint, AST check, or architectural fitness test).

### 1.2 Self-Healing Error Messages

* **MUST:** Custom linter and architectural boundary error messages must never merely state *"Forbidden usage of X."* Every error output **must** follow a structured format to enable autonomous agent self-correction within the CI loop:

  1. **Rule ID:** Unique identifier for the violated constraint.

  2. **Root Cause:** Concise explanation of why the pattern violates system invariants.

  3. **Exact Remediation:** Actionable code snippet or standard API replacement.

## 2. Architectural Boundaries & API Surface Area Control

### 2.1 Ban Nuance-Heavy Primitives

* **MUST NOT:** Product/application code must not directly invoke low-level primitives prone to state desynchronization or race conditions (e.g., raw `useEffect` in React product components).

* **MUST:** All complex side effects, lifecycle orchestration, and state synchronization **must** be encapsulated within the internal platform/framework layer (Core SDK), exposing only declarative, pit-of-success APIs to product code.

### 2.2 Physical Directory Isolation & Unidirectional Dependencies

* **MUST:** Architectural boundaries must be explicitly enforced via directory structure (e.g., strict separation between `core/`, `domain/`, `ui/`, or `main/` vs. `renderer/`).

* **MUST:** CI pipelines must enforce dependency graph validation (e.g., via `dependency-cruiser` or module boundary rules). Any cross-layer violation, reverse dependency, or circular dependency **must** fail the build immediately.

### 2.3 Zero-Comment & No Escape Hatches Policy

* **MUST NOT:** Inline comments used to justify patchy workarounds are strictly prohibited (targeting a $99\%$ reduction in inline comments). Using `setTimeout` to resolve asynchronous timing/race conditions, or unapproved suppression directives (`@ts-ignore`, `eslint-disable`), is forbidden.

* **MUST:** Code structure and type signatures must be self-documenting. Any unavoidable suppression directive **must** be bound to an expiration threshold and a tracked tech-debt ticket validated by CI.

## 3. Evidence-Based PR Review Gate

### 3.1 Review Verification Artifacts, Not Raw Diffs

* **SHOULD NOT:** Reviewers should not spend engineering cycles reading routine agent-generated implementation diffs line-by-line.

* **MUST:** Any PR modifying user-facing flows or core state machines **must** automatically attach at least one runtime verification artifact to the PR description prior to merge:

  1. **UI / E2E Execution Recording:** Video or screenshot sequence captured autonomously via Chrome DevTools Protocol (CDP) or headless drivers.

  2. **Visualized Statechart:** Auto-generated state machine topology diagram reflecting the updated state transitions.

  3. **Performance Benchmark Diff:** Automated comparison proving zero regression in cold-start time, memory footprint, or P99 latency.

### 3.2 Formal & Property-Based Verification

* **MUST:** Core modules governing cross-device synchronization, distributed locks, or financial state machines **must** be backed by TLA+ model specifications or formal invariant checks.

* **SHOULD:** Foundational algorithms and high-frequency UI components should employ property-based testing (fuzzing) to surface edge cases automatically.

## 4. Legacy Codebase Evolution

### 4.1 The Ratchet Principle

* **MUST NOT:** Full-stop, ground-up rewrites of legacy systems are strictly prohibited.

* **MUST:** Legacy repositories shall be governed via a monotonic "ratchet" mechanism:

  * Existing tech debt may be grandfathered into a static baseline.

  * All newly created or modified files **must** comply $100\%$ with RFC-001. Once an anti-pattern is eradicated from a module, its corresponding lint rule is locked globally so technical debt decreases monotonically.

## Appendix: Automated CI/CD Merge Gate Checklist

Every Pull Request targeting `main` must pass all automated gates below before qualifying for fast-track human sign-off or auto-merge:

* \[ \] **Static Gate 1 (Architecture):** Module dependency graph verified; zero boundary violations.

* \[ \] **Static Gate 2 (API Hygiene):** Zero banned primitives (e.g., raw `useEffect`), zero justification comments, zero unauthorized type assertions.

* \[ \] **Verification Gate 3 (Artifacts):** Runtime video/screenshots, statechart topology, or benchmark snapshots attached to PR.

* \[ \] **Verification Gate 4 (Invariants):** Unit tests, property-based tests, and formal state checks passing.
